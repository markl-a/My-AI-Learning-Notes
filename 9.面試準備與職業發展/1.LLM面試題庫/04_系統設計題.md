## 1. 企業 RAG 知識庫(10M docs, 1K QPS, 多租戶)

**題目**: Design a multi-tenant enterprise RAG system serving 10M documents across 500 tenants, 1K QPS peak, p99 latency < 2s, with strict per-tenant data isolation.

**需求釐清問題**:
- 文件格式(PDF / Office / Confluence)?是否要 OCR / 表格?
- 更新頻率(real-time vs 每日 batch)?
- 是否需要 citation / 權限過濾(ACL)?
- 模型選擇是 self-host 還是 API?預算上限?

**量級估算**: 10M docs × 平均 5KB chunk × 10 chunks/doc = **500M vectors**。1536 維 fp16 = 1.5TB(壓縮 PQ 後 ~300GB)。1K QPS × 平均 4K token output × $0.01/1K = **$144/小時 LLM 成本**。Embedding 重建 10M doc 約 8 小時(A100 × 8)。

**架構**:
```
   Client ─► API GW (rate limit per tenant) ─► Query Router
                                                    │
                ┌───────────────────────┬───────────┴────────┐
                ▼                       ▼                    ▼
         Embedding Svc          Hybrid Retriever      Re-ranker (Cohere)
         (bge-m3 GPU)           (Qdrant + BM25)       (GPU pool)
                                       │
                                       ▼
                              Tenant-partitioned shards
                                       │
                                       ▼
                              LLM Orchestrator ─► vLLM / OpenAI
                                       │
                                       ▼
                              Citation + Guardrail
```

**核心選型**: **Qdrant** 多 collection 做 tenant 隔離(避免 metadata filter 拖慢);**bge-m3** 支援 dense+sparse+ColBERT 三路;**BM25 via OpenSearch** 補長尾關鍵字;**Redis** 快取熱門 query embedding;**Kafka** 跑文件 ingest pipeline。

**Bottleneck & Trade-off**: 大租戶 (1M docs) vs 小租戶 (100 docs) 共用 shard 會 noisy neighbor → 分 **dedicated / pooled tier**。Re-ranker 是 latency 殺手,top-k=100→20 才送 cross-encoder,並用 batch=8 攤平 GPU。

**進階考點**: 文件權限(row-level ACL 怎麼在 vector search 做)、增量索引(soft-delete + tombstone)、評估(RAGAS + faithfulness)、跨語言檢索、prompt injection 防禦。

## 2. LLM API 閘道(類 LiteLLM / OpenRouter)

**題目**: Design an LLM API gateway that routes traffic across 20+ providers (OpenAI, Anthropic, Bedrock, self-hosted), with unified billing, rate limiting, fallback, and cost analytics. 5K QPS, 99.9% SLA.

**需求釐清**: 是否要 streaming?需不需要 prompt cache 跨 provider?是否做 semantic cache?隱私(PII 過濾)?

**量級估算**: 5K QPS,平均 request 8K token,output 2K token。日 token 量 **~10B**,假設 blended $5/1M = **$50K/day**。Log 每 request 20KB → 8.6TB/day 進 OLAP。SSE 連線數同時 ~50K(平均 10s)。

**架構**:
```
       User Key ─► Envoy (mTLS, ratelimit)
                       │
                       ▼
              Auth & Quota Service ─► Postgres + Redis
                       │
                       ▼
              Router (cost / latency / fallback)
                       │
            ┌──────────┼────────────┐
            ▼          ▼            ▼
        OpenAI     Anthropic    vLLM cluster
            │          │            │
            └──────────┴────────────┘
                       │
                       ▼
              Streaming Aggregator (SSE)
                       │
                       ▼
              Usage Logger ─► Kafka ─► ClickHouse
```

**核心選型**: **Envoy** 處理 connection-level rate limit;**Redis Cluster** 做 token bucket;**ClickHouse** 存使用量(每秒寫 5K + 高基數 group by);**OpenTelemetry** trace 跨 provider。Fallback 用 **circuit breaker + retry budget**,避免雪崩。

**Bottleneck & Trade-off**: SSE 長連線吃 fd,單機 65K 上限 → 用 **L4 LB + connection draining**。Cost accounting 必須在 stream 結束時統計 token,否則 client cancel 漏算 → **token-by-token incremental counter**。

**phantom-mesh 對應決策**: phantom-mesh 採 **provider abstraction layer**,Anthropic / OpenAI / Gemini / Bedrock 統一在 `ProviderAdapter` interface,SSE streaming 用 backpressure-aware async generator,cost tracking 用 token-level Prometheus counter(`llm_tokens_total{provider,model,tenant}`),fallback 用 **priority list + health probe**,失敗 3 次自動降級到下一個 provider。跨平台 build chain 用 **Nix + cross-compilation** 確保 Linux/macOS/Windows agent 二進位一致。

**進階考點**: Semantic cache(GPTCache + redis vector)、prompt routing(便宜模型先答,品質差再升級)、batch inference(對 async 任務聚合 10s window)、加密路由(payload 在 gateway 不解密)。

## 3. 客服 Voice Agent 系統(p50 < 500ms)

**題目**: Design a phone-based customer-service voice agent serving 10K concurrent calls, ASR → LLM → TTS pipeline, target p50 first-token latency < 500ms, supports barge-in.

**需求釐清**: 語言?是否需要 emotion / sentiment?是否要與 CRM 整合?call recording 合規(GDPR)?

**量級估算**: 10K concurrent × 平均 5 min call = **120K calls/hour**。語音 16kHz × 16bit = 32KB/s/call → 上行 320MB/s。GPU 上 ASR 用 Whisper-large-v3-turbo 約 50ms/chunk,LLM TTFT 200ms,TTS 100ms,網路 + buffer 150ms。

**架構**:
```
       PSTN ─► SIP Gateway (FreeSWITCH) ─► Media Server
                                              │
                                  WebSocket / gRPC bidi
                                              │
                                              ▼
                              Session Orchestrator (per-call FSM)
                                              │
              ┌─────────────────────┬─────────┴──────┬──────────────┐
              ▼                     ▼                ▼              ▼
         VAD + ASR              LLM (vLLM)         TTS           Barge-in
         (Whisper)              streaming        (Sonic)         detector
              │                     │                │
              └─────► Tool calls ◄──┘                │
                          │                          ▼
                          ▼                    Audio frames
                    CRM / Order API           back to caller
```

**核心選型**: **streaming everything**——ASR 用 partial transcripts,LLM speculative decoding,TTS 用 **Cartesia Sonic / ElevenLabs flash**(150ms TTFB)。VAD 用 **Silero**,barge-in 偵測到使用者說話立刻 cancel TTS stream。

**Bottleneck & Trade-off**: TTFT 200ms 對 LLM 是極限 → **prefill 預熱**(系統 prompt 已快取)+ 小模型(8B) for 簡單意圖,複雜問題再 escalate。GPU 排程用 **continuous batching** 但 voice 對 tail latency 敏感,需設 SLA-aware scheduler 拒收新 request。

**phantom-mesh 對應決策**: phantom-mesh 的 streaming SSE 設計可直接套用——`AsyncIterator` 包裝跨 provider stream,**chunk-level cancel token** 讓 barge-in 在 50ms 內中斷 LLM 生成。Cost tracking 在 streaming 過程逐 token 累計,call 結束時 flush 到 billing topic。

**進階考點**: 雙工對話(full-duplex)、情緒適配 TTS、call summary 後處理、fraud detection(voice clone 偵測)、合規錄音脫敏。

## 4. AI Code Review 服務(< 60s 反饋)

**題目**: Design a GitHub-integrated AI code review service that posts inline comments on PRs within 60s, supports 50K repos, 100K PRs/day.

**需求釐清**: 支援哪些語言?是否需要 build / 測試結果?是否要學習 reviewer 風格(personalization)?

**量級估算**: 100K PR/day = 1.16 QPS 平均、burst 10+。平均 PR 500 LOC + 5 file context = 20K token input,output 2K → 每 PR $0.06。日成本 **$6K**。Webhook 必須在 10s 內 ACK GitHub。

**架構**:
```
   GitHub Webhook ─► API (ACK 200 instantly)
                          │
                          ▼
                    Job Queue (SQS / Redis Stream)
                          │
                          ▼
                  Worker Pool (k8s HPA)
                  ┌───────┴────────┐
                  ▼                ▼
            Git Clone          Static Analyzer
            + diff parse       (semgrep, ruff)
                  │                │
                  └────────┬───────┘
                           ▼
                  Context Builder (tree-sitter + repo embedding)
                           │
                           ▼
                  LLM (Claude / GPT-4) with tools
                           │
                           ▼
                  Comment Poster (GitHub API, rate-limited)
```

**核心選型**: **tree-sitter** 抓 function boundary 比硬切 diff 好;**repo-level 向量索引**(增量更新)讓 LLM 看到 caller / callee;**semgrep** 先過一輪規則類問題,LLM 專注設計層;**Redis Stream** 做 job queue 支援優先級(付費客戶優先)。

**Bottleneck & Trade-off**: GitHub API rate limit 5000/hour/app → 用 **GitHub App** 每 install 獨立 quota。大 PR (5000 LOC) 超過 context window → **分塊 + map-reduce**,或拒答只給 summary。LLM 幻覺 line number → 強制 structured output + post-validation。

**進階考點**: Incremental review(只 review 新 commit)、self-consistency(同一段跑 3 次取交集減少噪音)、學習 organization style(few-shot from merged PR)、SAST 整合、licence detection。

## 5. 多 Agent Research 系統(Deep Research 類)

**題目**: Design a multi-agent research system that takes a query, spawns sub-agents to search and synthesize a 5-10 page report in 5-15 min, citing sources.

**需求釐清**: 來源限定(web only? 內部 doc?)?是否需要 user-in-the-loop?報告格式(markdown / docx)?

**量級估算**: 單次 task 平均 200 次 LLM 呼叫(planner + 10 sub-agents × 20 turns)+ 500 次 web fetch。Token 用量 ~5M/task,成本 **~$15/task**。並行 task 1K → 需 100K req/min 容量。

**架構**:
```
       User Query ─► Lead Agent (planner)
                           │
                           ▼
                  Task Decomposer ─► Plan Tree
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
         Sub-agent 1   Sub-agent 2   Sub-agent N
         (search +      (PDF read)   (code exec)
          summarize)
              │            │            │
              └─────► Shared Memory ◄───┘
                     (vector + KV)
                           │
                           ▼
                  Synthesizer Agent ─► Report
                           │
                           ▼
                  Citation Verifier
```

**核心選型**: **LangGraph / OpenAI Agents SDK** 做 stateful orchestration;**Brave / Tavily Search API** 抓網頁;**Playwright** 跑 JS 渲染頁;**共享 vector memory** 讓 sub-agent 避免重複搜尋;**checkpoint to S3** 支援 resume(15 min 任務不能因為一次 OOM 全丟)。

**Bottleneck & Trade-off**: Sub-agent 失控 token 用量 → 每個 sub-agent 設 **budget cap**(token + 步數),超過就強制 finalize。Web fetch 是延遲主因 → 並行 50,但 robots.txt + per-domain ratelimit 必守。Citation hallucination 是最大失分點 → **retrieve-then-quote**,任何 claim 必須在 retrieved chunk 找到原文。

**phantom-mesh 對應決策**: phantom-mesh 的 multi-agent layer 採 **DAG-based plan + worker pool**,plan 序列化成 protobuf 存 SQLite,任一 worker crash 由 supervisor 從 checkpoint 重啟。跨 provider fallback 在 worker 層做,單一 sub-agent 失敗自動換 model 重試 2 次。

**進階考點**: Plan-and-execute vs ReAct trade-off、self-reflection loop、parallel-vs-sequential 決策、報告品質評估(LLM-as-judge + 人工 rubric)、抗 prompt injection from web content。

## 6. Document Understanding 服務(ColPali 路線)

**題目**: Design a document QA service for PDF/Excel/scanned docs (with charts, tables, multi-column), serving 500 QPS, p95 < 3s, using vision-language models (ColPali / ColQwen).

**需求釐清**: 文件大小上限?是否要修改、簽核?多語?是否輸出座標(highlight)?

**量級估算**: 平均文件 20 頁,每頁 patch embedding 1030 × 128 維 = 132KB/page。10M pages → **1.3TB**(壓縮後 ~300GB)。VLM 推論每頁 1.5s on A100 → 用 prefetch + cache hit rate 70%。

**架構**:
```
    Upload ─► S3 ─► Ingest Worker
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
         PDF → image           Layout parser
         (pdf2image)           (option)
              │                     │
              ▼                     ▼
         ColPali Encoder ─► Multi-vector store
         (page-level)        (Vespa / Qdrant MV)
                                    │
                                    ▼
                            Late-interaction Search
                                    │
                                    ▼
                            VLM (Qwen2-VL) for answer
                                    │
                                    ▼
                            Bbox + cite + answer
```

**核心選型**: **ColPali / ColQwen2** 跳過 OCR 直接 patch embed,對 chart / table 比 text pipeline 好 30%+。**Vespa** 原生支援 multi-vector late interaction(MaxSim),Qdrant 也有但較新。**Qwen2-VL 72B** 做 generation;**vLLM 0.6+** 支援 VLM serving。

**Bottleneck & Trade-off**: Late interaction 計算量大(1030 × top-100),用 **two-stage: pooled vector ANN top-1000 → MaxSim rerank top-100**。儲存爆炸 → **binary quantization**(1bit per dim)壓 32 倍。

**進階考點**: Chart-to-data 結構化、表格跨頁合併、手寫支援、版面差異(報告 vs invoice)的領域微調、增量更新策略。

## 7. GraphRAG 知識圖譜 SaaS

**題目**: Design a SaaS where users upload documents and get an auto-built knowledge graph + QA. Support 100K tenants, average 1K docs each, real-time graph queries.

**需求釐清**: 是否允許用戶定義 schema?是否要視覺化?Update 是 full rebuild 還是 incremental?

**量級估算**: 100K × 1K docs = **100M docs**。Entity extraction 每 doc 平均 50 entity + 100 relation,共 **5B nodes, 10B edges**。Build 一次 ~$0.1/doc → 全量 $10M(分期建)。Query QPS 500 平均。

**架構**:
```
    Upload ─► OCR / Parse ─► Chunker
                                  │
                                  ▼
                       Entity & Relation Extractor (LLM)
                                  │
                       ┌──────────┴──────────┐
                       ▼                     ▼
                  Entity Resolver        Community Detector
                  (embedding +           (Leiden algo)
                   exact match)
                       │                     │
                       └──────────┬──────────┘
                                  ▼
                          Graph Store (Neo4j / Neptune)
                                  │
                                  ▼
                          Hybrid Query Engine
                          (Cypher + Vector + Text)
                                  │
                                  ▼
                          LLM Synthesizer
```

**核心選型**: **Microsoft GraphRAG** 模式:local search(entity 鄰居)+ global search(community summary)。Entity 用 **embedding 0.85 threshold** 做合併,衝突進人工 review queue。**Neo4j** 對 100M+ node 需 enterprise cluster,成本高 → 用 **TigerGraph / KuzuDB** 或 ArangoDB。

**Bottleneck & Trade-off**: Entity resolution 是 O(N²) → 用 **blocking + LSH** 先粗篩。Community detection 對大 graph 跑一次數小時 → **incremental Leiden** 或定期 batch。多租戶 graph 完全隔離(每 tenant 一個 DB)成本爆,共享需要嚴格 ACL。

**進階考點**: Schema-free vs schema-guided extraction、temporal graph(時間版本)、graph + vector 混合排序、GraphRAG vs Vector RAG 何時用哪個、可解釋性(顯示推理路徑)。

## 8. LLM 訓練資料合成平台

**題目**: Design a synthetic data generation platform (commercialized distilabel) that generates 1B tokens/day of SFT / preference data, supports multi-step pipelines, quality filtering, 100+ teams.

**需求釐清**: 領域(code? math? safety?)?是否需要 human-in-the-loop?輸出格式(JSONL / parquet / HF Hub)?

**量級估算**: 1B token/day,假設 Llama-70B self-host A100×8 throughput 5K tok/s → **23 卡時/小時**,200+ A100 同時跑。Pipeline 中位數 5 步,每筆樣本平均 10K token,日產 100M sample。

**架構**:
```
   Pipeline DSL (YAML) ─► Compiler ─► DAG
                                       │
                                       ▼
                                  Scheduler (Ray / Argo)
                                       │
                       ┌───────────────┼───────────────┐
                       ▼               ▼               ▼
                  Generator       Critic / Judge   Filter
                  (vLLM pool)     (smaller LLM)    (heuristic + dedup)
                       │               │               │
                       └───────────────┴───────────────┘
                                       ▼
                              Quality scorer (reward model)
                                       │
                                       ▼
                              Dataset Store (Iceberg / HF)
                                       │
                                       ▼
                              Lineage & versioning
```

**核心選型**: **Ray Data** 跨 GPU 大規模 map;**vLLM** + prefix caching(prompt 共用 system instruction);**MinHash dedup** + **n-gram filter**;**reward model**(Llama-3-RM / GRM)打分;**DVC / lakeFS** 做資料版本。

**Bottleneck & Trade-off**: GPU 利用率是錢,**continuous batching + prefix cache** 必開,instruction-heavy pipeline 可拉到 90%+。Critic 拒絕率高會浪費 generator 算力 → 把 critic 改 inline judge token(讓 generator self-critique)。

**進階考點**: Constitutional AI、self-instruct vs evol-instruct、contamination detection(防止 test set 洩漏)、red-teaming pipeline、license tracking(用 Llama-3.1 生資料的下游限制)。

## 9. Multi-tenant LoRA Serving(S-LoRA, 1000 個 adapter)

**題目**: Design a serving system that hosts 1000 LoRA adapters on top of a single base model (Llama-70B), supports per-request adapter selection, 2K QPS, p95 < 1s TTFT.

**需求釐清**: Adapter rank 範圍(8/16/64)?是否允許動態 upload?是否需要 multi-LoRA per request(merge)?

**量級估算**: 1000 adapter × rank 16 × Llama-70B 80 層 × 2 (A,B) × 8192 dim × 2bytes ≈ **42GB** adapter pool。Base model fp16 140GB,需 2×A100-80G + adapter 放 host RAM,動態 swap 到 GPU。

**架構**:
```
   Request (adapter_id) ─► Router
                              │
                              ▼
                     Adapter Cache (LRU GPU + RAM)
                              │
                              ▼
                     Batch Builder (group by adapter)
                              │
                              ▼
                     S-LoRA Kernel (segmented gemm)
                              │
                              ▼
                     Base Model Forward
                              │
                              ▼
                     Token Stream Out
```

**核心選型**: **S-LoRA / Punica** 的 **Multi-LoRA batched kernel** 可同時 serve 不同 adapter 在同一 batch。**Triton kernel** 寫 segmented gemm 比 naive padding 快 5×。**GPU-RAM tiered cache**,熱 adapter 在 HBM,冷 adapter 在 host pinned memory,DMA 切換 < 5ms。

**Bottleneck & Trade-off**: Adapter cold start swap PCIe 頻寬限制 → batch 內若超過 N=8 個不同 adapter 退回 fallback path。Adapter 上傳要驗證 shape / safetensors safety,惡意 adapter 可能含 trojan → sandbox 檢測。

**進階考點**: QLoRA serving(adapter + base 量化混搭)、adapter composition(weighted merge)、cold start prediction(預測下一個 adapter)、與 speculative decoding 結合、A/B test framework。

## 10. AI 內容真實性驗證 API(C2PA + SynthID)

**題目**: Design an API that verifies whether an image / video / text was AI-generated, returning provenance chain (C2PA) and watermark detection (SynthID / Stable Signature). 10K QPS, sub-second response.

**需求釐清**: 支援哪些 modality?是否要做 deepfake detection(語意層)?是否提供修改檢測?

**量級估算**: 10K QPS,image 平均 2MB → 20GB/s ingress,需 CDN 緩衝。Watermark detector 每張 GPU 推論 30ms → 300 GPU。C2PA manifest 解析純 CPU,~5ms。

**架構**:
```
    Upload ─► CDN ─► Edge worker (C2PA quick check)
                                       │
                                       ▼
                              Provenance Validator
                              (C2PA cert chain)
                                       │
                              ┌────────┴────────┐
                              ▼                 ▼
                     SynthID Detector     Stable Signature
                     (Google text/img)    (Meta image)
                              │                 │
                              └────────┬────────┘
                                       ▼
                              Aggregator + Confidence
                                       │
                                       ▼
                              Audit Log (immutable, append-only)
```

**核心選型**: **C2PA Rust SDK** 在 edge 解析 metadata(快、可拒絕無 manifest 的內容);**SynthID** 需要與 Google 合作或自訓;**Sigstore** 簽 audit log 防竄改;**S3 Object Lock** WORM 存 evidence。

**Bottleneck & Trade-off**: Watermark recall vs false positive 互斥 → 提供 confidence 而非二元判定。內容被裁切 / 重壓縮會破壞 watermark → multi-model ensemble + 報告 "tampered" 而非 "not AI"。

**進階考點**: Adversarial attack(去浮水印)、跨模型偵測(別人家 watermark 抓不到)、法規(EU AI Act 第 50 條)、隱私(不存原圖只存 hash)、SDK 端側偵測(推給 client)。

## 11. Computer Use Agent SaaS(瀏覽器自動化 + 沙箱)

**題目**: Design a Computer-Use agent SaaS where users describe a task in natural language and an agent operates a browser to complete it. 5K concurrent sessions, must be safe and compliant.

**需求釐清**: 是否允許登入用戶帳號?支付場景?資料殘留?監管(GDPR / SOC2)?

**量級估算**: 每 session 一個 headless Chrome ~500MB RAM + 1 vCPU。5K concurrent → **2.5TB RAM, 5K vCPU** = ~80 台 m6i.16xlarge。每次 screenshot 用 Claude Sonnet,平均 30 步 = 30 次 vision call ~$0.5/task。

**架構**:
```
   User Task ─► Controller
                    │
                    ▼
              Session Manager ─► VM Pool (Firecracker microVM)
                    │                  ┌──────────────┐
                    │                  │ Chromium     │
                    │                  │ + VNC stream │
                    │                  └──────┬───────┘
                    ▼                         │
              Agent Loop                      │
              (screenshot ──────────────────┐ │
               + action prediction) ◄───────┤ │
                    │                       │ │
                    ▼                       │ │
              Tool execution ───────────────┘ │
              (click/type/scroll)              │
                    │                          │
                    ▼                          │
              Safety Gate ─► Compliance Audit ─┘
```

**核心選型**: **Firecracker microVM** 每 session 完全隔離,啟動 < 200ms,kill 後狀態歸零。**CDP (Chrome DevTools Protocol)** 控制瀏覽器比 Selenium 穩。**Claude Computer Use / OpenAI Operator API** 做動作預測。**Bright Data / proxy pool** 規避反爬與固定 IP。

**Bottleneck & Trade-off**: Vision LLM token 量大(每張截圖 ~1500 token)→ 30 步 task = 45K token,用 **screenshot diff + only-send-changed-region** 砍半。安全 vs 自動化:agent 可能被 phishing 騙做轉帳 → **action allowlist + 人工 confirm for high-risk**(轉帳、刪除、發 email)。

**進階考點**: 反 bot 偵測(指紋 / behavioral)、CAPTCHA 處理、session 接管(handoff to human)、replay & debug、Computer Use 與 API-first 混用(優先 API,UI 為 fallback)。

## 12. 個人 AI 助手:RAG + Agent + Memory

**題目**: Design a personal AI assistant (ChatGPT-class) with long-term memory across sessions, multi-modal (text/image/voice), tools, 100M MAU, p50 TTFT < 800ms.

**需求釐清**: Memory 顆粒度(fact / episode)?跨裝置同步?資料刪除權?未成年保護?

**量級估算**: 100M MAU, DAU 30M, 平均 20 turn/day = **600M turn/day = 7K QPS 平均, 70K peak**。每 user memory ~10K fact × 1KB = 10MB → **1PB 總量**。LLM 成本若全用 frontier 模型 $0.05/turn → $30M/day,須混合 routing。

**架構**:
```
   Mobile/Web ─► API GW ─► Session Service
                                  │
                                  ▼
                         Memory Retriever
                       ┌──────────┼──────────┐
                       ▼          ▼          ▼
                  Short-term   Long-term   Profile
                  (Redis)      (Vector +    (Postgres)
                                Graph)
                                  │
                                  ▼
                         Router (intent / cost / model tier)
                                  │
                       ┌──────────┼──────────┐
                       ▼          ▼          ▼
                  Cheap Model  Frontier   Tool Agent
                  (Haiku)      (Opus)
                                  │
                                  ▼
                         Memory Writer (async, dedup)
```

**核心選型**: **三層 memory**:working(in-context)/ episodic(向量 + 時間衰減)/ semantic(graph,人事物關係)。**MemGPT / Letta** 的 self-edit memory pattern。**Router** 用小分類器,80% 流量打便宜模型,複雜或長 context 才升級。**Cassandra** 存 chat history(寫多讀少 + 多區域)。

**Bottleneck & Trade-off**: Memory contamination(錯資訊污染長期記憶)→ memory write 需 LLM 自我驗證 + 用戶可編輯。Cost 是核心,Route 錯誤代價是品質,需 **online evaluation**(同樣 prompt 跑兩 tier,小模型贏才採用)。

**phantom-mesh 對應決策**: phantom-mesh 的 cost tracking 模式可直接搬:**per-user budget enforcement** 在 Router 前置檢查當日 spend,超過 quota 自動降級到便宜模型。Memory store 用 phantom-mesh 的 **append-only event log + materialized view**,所有 memory 變更可審計、可回放、可遺忘(GDPR delete = mark tombstone)。跨平台 build chain 保證 desktop / mobile / web client 都能共享同一份 memory schema。

**進階考點**: 多 device sync(CRDT)、安全(prompt injection 從 email 進來)、人格一致性、評估(longitudinal user satisfaction)、企業版 vs 個人版隔離。
