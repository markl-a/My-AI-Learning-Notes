## A. 模型選型與成本 (7 題)

### Q1: phantom-mesh 上線兩週後,LLM API 成本超過 budget 30%,你怎麼降?
**難度**: 高級 · **時間**: 10 分鐘

先看 cost tracking 儀表板拆 top consumers:多半 80% 成本來自 20% 路由。短期措施:對 cheap intent(摘要、分類、簡單 QA)用 router 降到 Haiku / DeepSeek-V3;打開 prompt cache(Anthropic ephemeral / OpenAI prefix cache)把 system prompt + tool schema 命中率拉到 70%+;max_tokens 收緊、stop sequence 補齊。中期:semantic cache(embedding 相似度 > 0.95 直接回 cache)、把 RAG context 從 top-20 砍到 top-5 + rerank。預期 40-50% 降幅。

---

### Q2: GPT-4o vs Claude 3.7 Sonnet vs DeepSeek-V3 對我的 use case 怎麼選?
**難度**: 中等 · **時間**: 8 分鐘

先反問 use case 三件事:延遲敏感度、tool calling 比例、輸出長度。Claude 3.7 Sonnet 在長 reasoning + tool use chain 穩定性最好(extended thinking 可控),但 TTFT 偏高、價格中上。GPT-4o 在 multi-modal 與 structured output 成熟,latency 平均最低。DeepSeek-V3 價格只有 1/10,中文與 code 任務追平 Sonnet 一截,但 function calling 偶爾 schema drift。phantom-mesh 的 provider fallback 設計就是不二選,跑 A/B 在自己 eval set 上量化勝率再決定主路由。

---

### Q3: self-host 開源模型 vs 用 API,break-even 點怎麼算?
**難度**: 高級 · **時間**: 10 分鐘

公式:`break-even tokens/月 = (GPU 月成本 + 維運人力) / (API 單價 - self-host 單 token 攤銷)`。以 Llama-3-70B + 2× H100 為例,月燒約 $6-8k(含電費 + 折舊 + SRE 0.2 人月),vLLM 滿載約 150-200 TPS。API 對手是 Sonnet 約 $3/M input + $15/M output。**break-even 通常落在 3-5 億 tokens / 月**,且需 80%+ utilization。低於這個量、或流量有 spike,API 永遠贏。phantom-mesh 採 hybrid:peak 走 API、batch 走 self-host。

---

### Q4: 客戶要求 SLA 99.9%,單一 provider 做不到,怎麼設計?
**難度**: 高級 · **時間**: 10 分鐘

multi-provider fallback chain 是基本盤。phantom-mesh 的做法:三層 — primary (Anthropic) → secondary (OpenAI) → tertiary (self-host 開源)。關鍵不是切換邏輯,而是 **觸發條件與一致性**:5xx / timeout (> p99) / rate limit 立刻 fail-fast 到下一層,中途 retry 限 1 次避免 cascading latency。Prompt 要寫成 provider-agnostic(避免 Anthropic-only 的 tool_use block 直接餵 OpenAI),tool schema 用 JSON Schema 中介層轉換。SLA 用 budget burn rate 監控,別等到 incident 才知道。

---

### Q5: 老闆問「我們要不要自己訓練一個 7B 模型超過 GPT-4」,怎麼回?
**難度**: 中等 · **時間**: 6 分鐘

直接給數字:GPT-4 等級的 pretrain 約 $50-100M、半年、200+ 人月。7B continued pretrain + SFT + DPO 在 **垂直領域** 是有可能超過 GPT-4 的(medical / legal / code 已有案例),但「全面超過」幾乎不可能。可行替代:用開源 70B base 做 domain SFT + RLHF,目標是「在我們 eval set 上勝率 > GPT-4」,成本可壓到 $100-300k。先給 PoC 預算 1 個月做可行性驗證,再決定要不要全押。

---

### Q6: phantom-mesh 的 cost tracking 怎麼設計才能精準到每個 user / feature?
**難度**: 高級 · **時間**: 8 分鐘

每個 API call 打 tag:`(user_id, feature, model, prompt_tokens, completion_tokens, cached_tokens, latency)`,寫進 time-series DB(ClickHouse / TimescaleDB)。**關鍵 trick**:cached token 要分開計價(Anthropic cache write 1.25× / read 0.1×),別跟一般 input token 混在一起算。輸出端三個 view:per-user(rate limit + billing)、per-feature(產品決策)、per-model(provider 健康度)。alert 規則:單 user / 小時超 budget 3× 自動降級到 cheap model。

---

### Q7: API call retry 策略沒設計好導致流量放大 3 倍,怎麼修?
**難度**: 中等 · **時間**: 6 分鐘

典型 anti-pattern:exponential backoff 沒設 jitter + max retry,加上 429 後整層往上 cascade retry。修法三步:(1) 客戶端 retry 上限 = 2,backoff 加 jitter (random 0-1s);(2) 區分 retryable error(5xx、network)vs non-retryable(4xx);(3) **circuit breaker** — 失敗率 > 50% 持續 30 秒直接 open 一分鐘,避免雪崩。phantom-mesh 在 provider fallback 層就內建 breaker,單 provider down 不會把整個 mesh 帶垮。

## B. RAG 生產問題 (8 題)

### Q8: 用戶說 RAG 答案不準,如何 debug?
**難度**: 高級 · **時間**: 12 分鐘

別猜,先拆 pipeline 每段量化:(1) **retrieval recall** — 把 ground truth 文件丟進 retriever,top-k 命中率多少?低於 80% 就是 retriever 問題;(2) **rerank precision** — top-5 中相關 doc 排名;(3) **generation faithfulness** — 用 RAGAS / TruLens 量答案與 context 一致性。常見根因順序:embedding 模型不夠強(換 bge-large / cohere-rerank)> chunk 切錯(語意斷裂)> query 與文檔語意 gap(加 HyDE / query rewriting)> LLM 幻覺(降溫 + 加 cite source instruction)。

---

### Q9: chunk size 多少合適?有沒有 magic number?
**難度**: 中等 · **時間**: 6 分鐘

沒有 magic number,但有 framework:**chunk size = 語意完整單元 × 1.5**。技術文檔(API doc)200-400 tokens、敘事文本(法律 / 醫療)600-1000、code 用 AST 切函數 / class、對話紀錄用 turn 切。**overlap 通常 10-20%**。實務上跑 ablation:固定 query set + ground truth,掃 [128, 256, 512, 1024] 看 retrieval recall@5 與 answer accuracy,挑 sweet spot。phantom-mesh 內建文檔類型偵測會 dynamic 調 chunk strategy。

---

### Q10: vector DB 從 100GB 漲到 10TB 怎麼遷移?
**難度**: 高級 · **時間**: 12 分鐘

100GB 還能塞單機 HNSW,10TB 必須 sharded + disk-based ANN。遷移路徑:(1) 評估 — Milvus / Qdrant cluster mode 或 Pinecone pod scaling;(2) **不要 stop-the-world** — 雙寫策略:新進文檔同時寫舊 + 新庫,backfill 舊資料分批跑(每天 500GB),用 shadow query 對比兩邊 recall;(3) index 選型 — 10TB 規模 HNSW 記憶體吃不消,改 IVF-PQ 或 DiskANN,接受 5-10% recall loss 換 100× 記憶體節省;(4) 全量切換前跑兩週雙讀 + diff alert。

---

### Q11: 新增 1M docs,全 reindex 還是 incremental?
**難度**: 中等 · **時間**: 6 分鐘

絕對 incremental。1M docs 全 reindex 要重算 embedding(假設 768d / 1M 約 30 GPU 小時)+ rebuild HNSW graph(線性 vs log,差幾十倍)。Incremental 流程:新文檔走 ingestion queue → embedding 服務 batch(每 batch 256 條)→ 寫入 vector DB 的 insert API(HNSW 支援動態插入)。**唯一例外**:embedding 模型升級必須全 reindex,這時候用 blue-green — 新庫並行建,完成後 atomic switch。

---

### Q12: 用戶問「上週的會議紀錄」,RAG 老是抓到三個月前的舊紀錄,怎麼解?
**難度**: 高級 · **時間**: 8 分鐘

純語意檢索沒有時間感。解法層層加:(1) **metadata filter** — 文檔索引時打 timestamp,query 解析出時間意圖後加 `where date >= last_week`;(2) **time-decay reranking** — final score = semantic_score × exp(-λ × age_days),λ 看 domain 調;(3) **query understanding** — 用 LLM 先解析 query 抽出 `{intent, time_range, entities}`,做 hybrid 查詢。會議紀錄場景強烈建議走 (1),metadata filter 比語意 boost 可靠太多。

---

### Q13: hybrid search(BM25 + vector)的權重怎麼調?
**難度**: 中等 · **時間**: 6 分鐘

別用線性加權(score 尺度不一致),用 **Reciprocal Rank Fusion (RRF)**:`score = Σ 1 / (k + rank_i)`,k 通常 60。或者跑 learned rank fusion — 蒐集 (query, doc, label) 資料訓一個 LightGBM 學最佳組合。經驗值:**短 query(關鍵字型)BM25 權重高,長 query(自然語言)vector 權重高**。phantom-mesh 內建 query 長度分類自動切兩種模式。最後一定要過 cross-encoder reranker(bge-reranker-large)把 top-20 重排到 top-5。

---

### Q14: RAG 答案經常 hallucinate 引用不存在的條款,怎麼根治?
**難度**: 高級 · **時間**: 10 分鐘

三層防線:(1) **prompt 層** — 強制 `cite [doc_id, chunk_id]`,沒 cite 的句子要求模型自己刪,使用 structured output 把 answer 拆成 claims 陣列每條帶 citation;(2) **post-hoc verification** — 生成後跑 NLI 模型(roberta-large-mnli)檢查每個 claim 對 context 是 entailment / neutral / contradiction,contradiction 直接 reject;(3) **citation grounding** — 把模型輸出的 cite 反查向量庫,確認 doc_id 真實存在且 chunk 內容支持該 claim。三層下來 hallucination rate 從 15% 降到 < 2%。

---

### Q15: 多語言 RAG,中英混雜文檔檢索效果差,怎麼辦?
**難度**: 高級 · **時間**: 8 分鐘

根因通常是 embedding 模型對非英文支持弱。換 multilingual embedding(bge-m3 / multilingual-e5-large),這類模型在 cross-lingual retrieval(中文 query 撈英文 doc)上 recall 翻倍。次要做法:**query translation** — 把 query 同時翻成中英兩版各撈一次再 fuse;**document-level language tag** — 索引時打 lang metadata,query 端依用戶語系優先撈母語文檔。code 文檔特別吃虧,建議 code chunk 用專用 embedding(CodeBERT / unixcoder)。

## C. Agent 故障 (7 題)

### Q16: Agent 卡在無限 tool call loop,怎麼防?
**難度**: 高級 · **時間**: 10 分鐘

三道防線:(1) **hard limit** — max_iterations = 10,超過直接終止回 fallback 訊息;(2) **重複偵測** — 把每輪 (tool_name, args_hash) 存 set,連續三次相同就 break(模型陷入 echo);(3) **token budget** — 累計 token 超 50k 強制收斂。但根因常在 prompt:tool description 不清楚導致模型分不清成功 / 失敗,要求 tool 回傳必須帶 `status: success/error/partial` + `next_suggested_action`。phantom-mesh 在 multi-agent 協調層統一管 budget,單 agent 爆了不會拖死整個 mesh。

---

### Q17: phantom-mesh 跑 multi-agent 任務,planner 與 executor 互相打架,怎麼解?
**難度**: 高級 · **時間**: 12 分鐘

「打架」通常兩種:(a) planner 改計畫太頻繁、(b) executor 自作主張改 task。修法是 **明確 contract**:planner 輸出 immutable task DAG(JSON),executor 只能在 task 內決定 tool,不能新增 task,要新增 task 必須 escalate 回 planner。實作上:planner 與 executor 用不同 system prompt + 不同模型(planner = Sonnet 強推理,executor = Haiku 快執行)。phantom-mesh 用 message bus(中央 coordinator)而非 agent-to-agent direct call,避免循環依賴。

---

### Q18: tool call JSON schema 偶爾失敗(模型輸出 malformed JSON),怎麼處理?
**難度**: 中等 · **時間**: 8 分鐘

第一手:用 provider 原生 structured output(OpenAI `response_format: json_schema` / Anthropic tool_use),強約束比 prompt-only 可靠 10×。仍然失敗時三層 fallback:(1) **JSON repair** — 用 `json-repair` library 修常見錯誤(尾逗號、未閉合引號);(2) **schema-guided retry** — 把 error message + 原始輸出餵回模型 "請修正成符合 schema 的 JSON";(3) **降級** — 改 free-form 文字 + regex 提取關鍵欄位。phantom-mesh 統計顯示 Sonnet 在 tool calling 上 schema 失敗率 < 0.3%,DeepSeek-V3 約 2%,需 retry。

---

### Q19: phantom-mesh 中 provider fallback 邏輯,如何避免「主 provider 偶發 timeout 就整批失敗」?
**難度**: 高級 · **時間**: 10 分鐘

關鍵設計:**hedged request**(對 latency-critical 路徑)— 主 provider 發出後等 p95 latency 仍未回應,並行打次 provider,誰先回用誰。一般路徑用 sequential fallback + circuit breaker。實作細節:(1) timeout 分層 — connection 5s / first-token 15s / total 60s;(2) **語意一致性** — fallback 後的 tool_use response 要正規化成統一格式(Anthropic block 與 OpenAI tool_calls 結構不同);(3) **idempotency key** — 避免 fallback 重發造成 side-effect double-execute。

---

### Q20: Agent 執行到一半 user cancel,如何優雅中止 in-flight tool calls?
**難度**: 高級 · **時間**: 8 分鐘

從 SSE 取消 → coordinator broadcast cancel → 各 in-flight tool 收 context.cancel() → 必要時呼叫 provider 的 stop API(OpenAI 支援 stream cancel)。tool 端必須是 cancellation-aware:長跑 shell command 用 process group kill、HTTP request 用 cancellable client。**坑點**:LLM provider 端即使前端 cancel,billing 仍會按已生成 token 計費,所以 cancel 越早越省。phantom-mesh 用 Go context + Rust tokio cancellation token 雙語言對齊。

---

### Q21: 給 Agent 50 個 tool,效果反而變差,為什麼?
**難度**: 中等 · **時間**: 8 分鐘

兩個根因:(1) **tool schema 占 context 過大** — 50 個 tool 描述可能佔 5-10k tokens,排擠真實任務 context;(2) **選擇困難** — 模型在相似 tool 間搖擺(例如 search_web vs search_internal vs search_kb 三個都長得像)。解法:**hierarchical tool routing** — 先讓 router LLM 從 50 個中選 5 個相關 tool,再把這 5 個 schema 傳給 executor。或者 tool 命名 + description 嚴格不重疊,加 "use this when X, NOT when Y" 對比範例。

---

### Q22: Agent memory 不斷膨脹,30 輪後 context 已經 100k tokens,怎麼壓縮?
**難度**: 高級 · **時間**: 10 分鐘

分層 memory 設計:(1) **short-term**(最近 5 輪原文保留);(2) **working memory**(中段對話自動 summarize 成 200 字 + 保留所有 tool result 結構化資料);(3) **long-term**(寫進 vector store,需要時 RAG 撈回)。實作時注意 tool_result 結構不能簡單砍掉,壓縮要保語意(用 LLM 做 lossy compression 並記錄 compression marker)。Anthropic 新的 prompt caching + memory primitive 可以把 cache hit 撐到 30 輪以上不重算。

## D. 推理延遲 (5 題)

### Q23: p99 TTFT 從 800ms 突然飆到 5s,排查路徑?
**難度**: 高級 · **時間**: 12 分鐘

照 layer 由外往內查:(1) **CDN / gateway**(看自家 metric vs provider status page,排除外部因素);(2) **prompt 長度突變** — 看近期 prompt token 分布,有無新 feature 灌長 context;(3) **cache hit rate 崩盤** — Anthropic ephemeral cache 5 分鐘 TTL,如果流量降到 cache 都過期,TTFT 翻倍很常見;(4) **provider 端 queue** — rate limit 觸發排隊;(5) **自家 KV cache 命中率**(self-host 場景)。phantom-mesh 內建 TTFT 分段打點(network / queue / first-token)直接定位。

---

### Q24: decode 速度慢,vLLM 還是 SGLang?
**難度**: 高級 · **時間**: 10 分鐘

看 workload。**vLLM** 在通用 batch serving、PagedAttention 記憶體效率最好,生態最成熟、社群 PR 多。**SGLang** 在 structured output(JSON / regex)、long shared prefix(RAG 大量重複 system prompt)、speculative decoding 上明顯快 1.5-2×,RadixAttention 對 prefix cache 命中極致。決策:如果 phantom-mesh 場景 70% 流量是 RAG + tool calling(prefix 高度重複),SGLang 勝;如果是雜亂多輪對話,vLLM 穩。先 benchmark 自家 trace 再選。

---

### Q25: streaming SSE 解析在 phantom-mesh 怎麼做才不會吃 CPU?
**難度**: 高級 · **時間**: 10 分鐘

幾個關鍵設計:(1) **不要每個 chunk 就 JSON.parse 整段** — SSE event 用 `data: ` 前綴切行,buffer 累積到 `\n\n` 才解析一次;(2) **Anthropic 與 OpenAI event 格式不同** — Anthropic 有 message_start / content_block_delta / message_stop 多種事件,需要狀態機;OpenAI 只有 delta;phantom-mesh 用 trait / interface 抽出統一 StreamEvent,各 provider adapter 翻譯;(3) **back-pressure** — 下游消費慢時,用 bounded channel 避免 buffer 爆掉。Rust 用 tokio mpsc、Go 用 chan with cap。

---

### Q26: 自家 7B 模型 throughput 才 30 TPS,benchmark 應該到 150 TPS,差在哪?
**難度**: 高級 · **時間**: 10 分鐘

排查清單:(1) **batch size = 1** — 沒開 continuous batching,單請求跑等於浪費 GPU;(2) **input 太長** — 長 input prefill phase 慢,看 prefill : decode 時間比;(3) **GPU utilization** — `nvidia-smi` 低於 70% 通常是 CPU-bound(tokenizer / sampling 在 CPU)或 IO bound;(4) **量化未啟用** — FP16 改 AWQ / GPTQ INT4,throughput 通常 2× 起;(5) **flash-attention 未開**;(6) **swap 到 CPU** — KV cache 滿了。逐項對齊 benchmark config。

---

### Q27: 用戶反映「答案出來很慢但其實 token 沒比較多」,怎麼診斷?
**難度**: 中等 · **時間**: 6 分鐘

差別在 TTFT 不是 total latency。打點看 `first_token_ms` 與 `tokens_per_sec`:如果 first_token_ms 占 80%+,是 prefill / queue 慢,不是 decode 慢。常見原因:(1) prompt cache miss(剛重啟服務 / TTL 過期);(2) provider 端高峰排隊;(3) 自家 vLLM prefill chunked 沒開,大 prompt 阻塞 batch。修法:streaming 一定要開、cache 命中率監控、prefill chunked。用戶感知速度是 TTFT 主導,絕對不是 total latency。

## E. 訓練問題 (5 題)

### Q28: 微調後在訓練集表現好,線上很差,典型 overfit,怎麼救?
**難度**: 高級 · **時間**: 10 分鐘

先確認真的是 overfit(train acc 高 / val acc 低)還是 distribution shift(線上資料分布跟訓練集不同)。Overfit 救法:(1) 降 epoch(LoRA fine-tune 常 1-3 epoch 就夠,跑 10 epoch 必爆);(2) 加 dropout / weight decay;(3) 資料增強;(4) early stopping 用 holdout val set。**Distribution shift 才是線上專案 90% 的真因** — 重採線上 query 1000 條,human label 後加入 train set 做 active learning,比調 hyperparam 有效 10×。

---

### Q29: DPO 訓練 reward collapse(輸出全變短 / 全變長),怎麼修?
**難度**: 高級 · **時間**: 10 分鐘

DPO 經典 length bias 問題。原因:preference data 中 chosen 系統性比 rejected 長,模型學到「長 = 好」。修法:(1) **length-normalized DPO** — loss 除以序列長度;(2) **IPO / KTO** — 改用對 length bias 更 robust 的變體;(3) **preference data 清理** — 確保 chosen / rejected 長度分布相近,差 > 2× 的 pair 丟掉;(4) **加 reference model KL 懲罰係數 β**(從 0.1 提到 0.5),拉住別偏離太遠。**並監控 reward margin 與輸出長度的 correlation**,警報 > 0.3 就介入。

---

### Q30: long context fine-tune 後短 context 表現變差,怎麼平衡?
**難度**: 高級 · **時間**: 10 分鐘

典型「災難性遺忘」。根因:long context SFT 資料分布太偏(全是 32k+ 樣本),模型在短輸入上 attention pattern 退化。修法:(1) **mixed-length training** — 訓練 batch 強制混入 30% 短樣本(< 2k tokens);(2) **replay buffer** — 保留原始 base model SFT 資料 10-20% 混入;(3) **YaRN / position interpolation** 而非全層重訓,只擴展位置編碼,主權重凍結。eval 時務必 short / medium / long 三段 benchmark 都跑,不能只看 long context recall(NIAH)。

---

### Q31: SFT 完成後想做 RLHF,但 reward model 訓不上去,acc 卡在 60%,怎辦?
**難度**: 高級 · **時間**: 10 分鐘

60% acc(隨機 50%)代表 reward model 幾乎沒學到東西。先檢查資料:(1) **annotator agreement** — 不同人標同 pair 一致率 < 70% 就是任務定義不清,reward model 上限就在這;(2) **chosen / rejected 太相似** — 抽 100 條人看,如果你自己也分不出哪個好,模型更不可能;(3) **base model 太弱** — reward model 建議用 SFT 後的模型同尺寸 init,不要用 base;(4) 改用 **DPO / ORPO** 跳過 reward model 階段,直接從 preference 學,工程複雜度大幅降低。

---

### Q32: continued pretrain 7B 模型注入領域知識,結果通用能力大降,怎麼救?
**難度**: 高級 · **時間**: 8 分鐘

純領域語料訓練必然遺忘通用能力。標準 recipe:(1) **資料配比 50% 領域 + 50% 高品質通用語料**(C4 / SlimPajama subset);(2) learning rate 壓到 base pretrain 的 10%(2e-5 級別),避免大幅更新;(3) **凍結 embedding + 部分 layer** 只訓中後段;(4) 訓完做 eval 雙軸 — 領域任務勝率 + MMLU / BBH 不能掉超過 3%。若已經訓壞,只能從 checkpoint 回滾或 model souping(把 base 與 finetuned weight 加權平均)。

## F. 安全與合規 (5 題)

### Q33: 用戶上傳含 PII(身分證、信用卡)的文檔到 RAG,怎麼處理?
**難度**: 高級 · **時間**: 10 分鐘

入口攔截 + 全鏈路脫敏:(1) **ingestion 階段** PII detection(Presidio / 自訓 NER)掃描,身分證 / 卡號 / 健保號 mask 成 token(如 `<CREDIT_CARD_1>`),並存 mapping 在加密 vault;(2) embedding / retrieval 都用 masked 版本,LLM 永遠看不到原文;(3) **output 階段** 再次掃描,防止模型從上下文線索還原;(4) **audit log** 所有 PII 觸及事件 7 年留存(金融合規);(5) 用戶側提供 "right to be forgotten" — 刪文檔時連 vector + cache + log 全清。

---

### Q34: prompt injection 怎麼偵測?用戶在輸入裡寫 "Ignore previous instructions"
**難度**: 高級 · **時間**: 10 分鐘

沒有銀彈,層層防禦:(1) **分離 user input 與 system prompt** — 用 XML tag 把 user input 包住 `<user_input>...</user_input>`,prompt 明示 tag 內視為資料不是指令;(2) **分類器** — 訓練 / 用現成的 prompt injection classifier(Lakera / promptguard)做入口過濾;(3) **least privilege** — agent 能呼叫的 tool 嚴格限縮,即使被劫持也只能做有限事;(4) **output 監控** — LLM 回應中出現「sure, here's the system prompt」這類 indicator 觸發 block;(5) **red team** — 持續對抗測試,蒐集 attack pattern 進 deny list。

---

### Q35: EU AI Act 上路,phantom-mesh 服務歐洲用戶要做哪些合規?
**難度**: 高級 · **時間**: 12 分鐘

依風險分類定義:LLM 屬 General-Purpose AI Model(GPAI),若服務量達門檻(10^25 FLOPs 或 systemic risk)額外要求。基本義務:(1) **transparency** — 用戶必須知道在跟 AI 互動,輸出內容若是 AI 生成需標記;(2) **technical documentation** — 訓練資料來源、模型卡、評估報告;(3) **copyright compliance** — 公開訓練資料摘要,respect opt-out signals;(4) **risk assessment** — 高風險場景(招聘、信評)需 conformity assessment;(5) **incident reporting** — 嚴重 incident 15 天內通報。phantom-mesh 本身是 orchestrator,主責在底層 provider,但需透傳 disclosure。

---

### Q36: 客戶要求「資料不出境」,但我們用 OpenAI / Anthropic API,怎麼辦?
**難度**: 中等 · **時間**: 8 分鐘

三條路:(1) **provider 的本地區域** — Azure OpenAI 有 EU region、AWS Bedrock 在多區域可選,Anthropic via Bedrock 在歐洲可承諾資料不出境;(2) **self-host 開源模型** — Llama-3 / Qwen / DeepSeek 部署在客戶 VPC,完全內網;(3) **混合** — sensitive query 路由到 self-host,non-sensitive 走 API。phantom-mesh 的 provider router 設計天然支援 — 在 request 上打 `data_residency: eu_only` tag,router 自動排除不合規 provider。合約上要求 provider 提供 BAA / DPA 文件。

---

### Q37: 模型輸出生成違法內容(誹謗、版權),公司被告,如何免責?
**難度**: 高級 · **時間**: 8 分鐘

技術上做不到 100% 免責,但可降低責任:(1) **content moderation** — 輸入 / 輸出都過 moderation API(OpenAI moderation / 自訓);(2) **clear disclaimer** — UI 明示 "AI 生成內容,使用者需自行查證";(3) **abuse rate limit** — 對單一 user 異常 pattern 自動 ban;(4) **audit trail** — 完整保留 prompt + output + user_id 至少 90 天,出事可追溯;(5) **保險** — AI liability insurance 開始有市場;(6) **TOS** 明確限制使用場景並要求用戶承擔生成內容責任。實務上美國 Section 230 / 歐洲 DSA 對 AI 平台責任界線仍在演進。

## G. 跨平台與部署 (3 題)

### Q38: phantom-mesh 跨平台 build chain(Rust core + Go services + TS frontend),怎麼維護?
**難度**: 高級 · **時間**: 12 分鐘

關鍵是 **單一 source of truth + 多平台輸出**。實作:(1) **monorepo** with `cargo workspace` + `go.work` + `pnpm workspace`,top-level Makefile / justfile 統一指令;(2) **schema 共享** — protobuf / JSON Schema 定義 LLM message、tool call、SSE event,各語言用 codegen(prost-rs / protoc-gen-go / ts-proto)生成 binding,避免手寫 drift;(3) **CI matrix** — GitHub Actions 跑 linux/macos/windows × x86/arm64;(4) **release** — Rust 用 cargo-dist 出多平台 binary、Go 用 goreleaser、TS 用 tsup + npm publish。phantom-mesh 統一在 release 階段做 sign + SBOM。

---

### Q39: 邊緣部署 70B 模型(離線、車載 / IoT 場景)怎麼做?
**難度**: 高級 · **時間**: 12 分鐘

70B 在邊緣幾乎不現實,先挑戰需求 — 真的需要 70B 還是 7B 就夠?若必須:(1) **量化到極致** — INT4 (GPTQ / AWQ) 把模型壓到 35GB,Q3_K_M 壓到 28GB 可上 Jetson AGX Orin 64GB;(2) **MoE 分片** — DeepSeek-V2 等 MoE 只激活部分專家,有效參數量遠小於總量;(3) **speculative decoding** — 邊緣用小 draft model 加速;(4) **knowledge distillation** — 把 70B 蒸到 13B 或 7B,任務特化通常掉 < 5%;(5) **離線約束** — 預先快取 system prompt 與常用 RAG context。實務上絕大多數 IoT / 車載走 distill + 量化 7-13B 路線。

---

### Q40: Apple Silicon vs CUDA vs ROCm 取捨,phantom-mesh 怎麼選?
**難度**: 高級 · **時間**: 10 分鐘

按使用情境分:(1) **開發 / 本地原型** — Apple Silicon (M3 Max / M4 Max),unified memory 128GB 跑 70B Q4 完全可行,llama.cpp / MLX 生態成熟,功耗極低;(2) **生產推理** — CUDA 仍是王者,vLLM / SGLang / TensorRT-LLM 全套圍繞 CUDA,生態深度差距 3+ 年;(3) **ROCm**(AMD MI300X)— 性價比好(MI300X 192GB HBM vs H100 80GB),vLLM 已支援但 corner case 多,適合大型部署談價有籌碼;(4) **訓練** — CUDA 唯一務實選擇。phantom-mesh runtime 抽象出 device backend,本地 dev 用 MLX、prod 用 CUDA,程式碼一致。

---

## 應對策略總結

1. **拆解 pipeline** — 任何「不準 / 慢 / 貴」問題,第一步永遠是分段量化,別猜根因
2. **fallback 即基礎建設** — multi-provider / multi-strategy 是生產系統的呼吸,不是 nice-to-have
3. **成本即指標** — cost per query 應該與 latency、accuracy 並列為核心 SLI
4. **安全即內建** — PII / injection / 版權,從 ingestion 第一步就要考慮,不是事後補
5. **eval 驅動決策** — 模型選型、chunk size、hybrid 權重,所有 magic number 都該用自家 eval set 跑 ablation
