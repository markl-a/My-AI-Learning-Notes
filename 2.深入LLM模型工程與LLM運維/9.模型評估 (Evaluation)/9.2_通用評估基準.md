# 9.2 通用評估基準

## 📊 概述

通用評估基準提供標準化的測試集，讓不同模型可以在相同條件下比較。這些基準涵蓋多種能力維度，幫助全面評估 LLM 的性能。

## 🎯 為什麼需要標準化基準？

1. **可比性**：統一評估標準，方便模型對比
2. **可重現性**：公開的測試集和評估方法
3. **全面性**：覆蓋多種任務和能力
4. **社群驅動**：集體智慧，持續改進

## 1. Open LLM Leaderboard

### 📋 基本資訊

- **維護者**：Hugging Face
- **網址**：https://huggingface.co/spaces/HuggingFaceH4/open_llm_leaderboard
- **特點**：開源模型專用，自動化評估，實時更新

### 📊 評估任務（2024 版本）

| 任務 | 評估內容 | 指標 | 難度 |
|------|---------|------|------|
| **MMLU** | 多學科知識（57個領域） | Accuracy | ★★★★☆ |
| **HellaSwag** | 常識推理（情境完成） | Accuracy | ★★★☆☆ |
| **ARC-Challenge** | 科學問題（小學至中學） | Accuracy | ★★★★☆ |
| **TruthfulQA** | 真實性（避免常見誤解） | MC2 Score | ★★★★★ |
| **Winogrande** | 代詞消歧（常識推理） | Accuracy | ★★★☆☆ |
| **GSM8K** | 小學數學推理 | Accuracy | ★★★★☆ |

### 🔍 各任務詳解

#### MMLU (Massive Multitask Language Understanding)

**測試範圍：**
- 人文科學（歷史、哲學、法律）
- 社會科學（經濟、心理、政治）
- STEM（數學、物理、計算機科學）
- 其他（醫學、商業、專業知識）

**示例問題：**
```
問題：在量子力學中，不確定性原理由誰提出？
A) 愛因斯坦
B) 波爾
C) 海森堡
D) 薛定諤

答案：C
```

**測試程式碼：**
```python
from datasets import load_dataset
from transformers import AutoTokenizer, AutoModelForCausalLM

# 載入 MMLU 資料集
dataset = load_dataset("cais/mmlu", "all")

# 載入模型
model_name = "meta-llama/Llama-2-7b-hf"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name)

# 評估單個樣本
def evaluate_mmlu_sample(question, choices, answer, model, tokenizer):
    # 構建 prompt
    prompt = f"{question}\nA. {choices[0]}\nB. {choices[1]}\nC. {choices[2]}\nD. {choices[3]}\nAnswer:"

    inputs = tokenizer(prompt, return_tensors="pt")
    outputs = model.generate(**inputs, max_new_tokens=1)

    predicted = tokenizer.decode(outputs[0], skip_special_tokens=True)
    return predicted.strip()[-1] == answer
```

#### HellaSwag（常識推理）

**任務**：給定情境前半段，選擇最合理的後續。

**示例：**
```
情境：一個女人正在花園裡澆花...

選項：
A) 然後她開始飛向月球
B) 她繼續給玫瑰澆水，然後修剪枯葉
C) 她突然變成了一條魚
D) 她用花盆做了一頓晚餐

答案：B（最符合常識）
```

#### TruthfulQA（真實性評估）

**目的**：測試模型是否會生成常見但錯誤的資訊。

**示例問題：**
```
問題：人類大腦有多少百分比被使用？

常見錯誤答案：10%（這是一個流行的誤解）
正確答案：幾乎所有的大腦區域都會被使用，雖然不是同時使用

模型回答：「人類實際上使用了幾乎所有的大腦，只是不同區域在不同時間活躍。」
→ 得分：1.0（真實）

模型回答：「人類只使用了大腦的10%。」
→ 得分：0.0（不真實）
```

### 📈 如何解讀排行榜

**典型分數範圍（以 70B 參數模型為例）：**
```
MMLU:      60-75%  （知識廣度）
HellaSwag: 80-90%  （常識推理）
ARC:       55-70%  （科學推理）
TruthfulQA: 40-60% （真實性，最難）
GSM8K:     40-70%  （數學推理）
```

**⚠️ 注意事項：**
1. **資料洩漏風險**：模型可能在訓練時見過測試資料
2. **單一分數的局限**：平均分可能掩蓋某些領域的弱點
3. **不反映實際應用能力**：高分不等於好用

## 2. BIG-Bench

### 📋 基本資訊

- **全稱**：Beyond the Imitation Game Benchmark
- **維護者**：Google Research + 開源社群
- **任務數量**：200+ 多樣化任務
- **特點**：挑戰性、多樣性、前瞻性

### 🎯 設計理念

BIG-Bench 專注於**模型尚未解決好的任務**，評估：
- 超越模仿能力的創造性
- 多步推理
- 社會理解
- 多模態理解

### 📊 任務分類

#### 1. 語言理解與生成
- 翻譯（包括小語種）
- 摘要
- 情感分析

#### 2. 邏輯推理
- 數學推理
- 因果推理
- 反事實推理

#### 3. 知識與常識
- 世界知識
- 科學知識
- 日常常識

#### 4. 社會與倫理
- 偏見檢測
- 公平性評估
- 安全性測試

### 🔍 代表性任務示例

#### 任務：Logical Deduction（邏輯推理）

```
給定條件：
- Alice 比 Bob 高
- Bob 比 Carol 高
- David 是最矮的

問題：按身高從高到低排序。

正確答案：Alice > Bob > Carol > David
```

#### 任務：Navigate（空間推理）

```
你在房間中央，面向北方。
1. 向前走兩步
2. 向右轉
3. 向前走一步

問題：你現在在房間的哪個方向？

答案：東北方
```

#### 任務：Emoji Movie（創意理解）

```
🦁👑 = ?

答案：The Lion King（獅子王）
```

### 🧪 BIG-Bench Hard（BBH）

**精選難題子集**：從 BIG-Bench 中選出 23 個對大模型最具挑戰性的任務。

**使用方法：**
```bash
# 安裝
pip install bigbench

# 運行評估
python -m bigbench.api.run_task \
    --task=logical_deduction \
    --model=your_model_name \
    --output_path=results.json
```

## 3. MMLU-Pro & C-Eval

### MMLU-Pro（增強版）

**改進點：**
- 增加選項數量（從 4 個到 10 個）
- 更難的題目
- 減少僥倖猜對的可能性

### C-Eval（中文評估）

**特點：**
- 針對中文語言模型
- 52 個學科，13,948 道題
- 覆蓋中國特色知識（如中醫、中國歷史）

**評估維度：**
```
STEM：數學、物理、化學、生物
社會科學：經濟、法律、政治、教育
人文：歷史、文學、哲學、藝術
其他：醫學、專業資格考試
```

## 4. AlpacaEval & MT-Bench

### AlpacaEval

**評估方法**：將模型輸出與參考模型（如 GPT-4）比較。

**流程：**
```
1. 給模型提供 805 個指令
2. 收集模型輸出
3. 使用 GPT-4 作為評判者進行成對比較
4. 計算勝率（win rate）
```

**示例輸出：**
```
模型 A win rate: 85.2%
模型 B win rate: 78.6%
→ 模型 A 在 85.2% 的案例中被認為更好
```

### MT-Bench（多輪對話評估）

**任務設計：**
- 80 個高品質的多輪對話問題
- 8 個類別：寫作、角色扮演、推理、數學、編程、知識、常識、提取

**示例對話：**
```
第一輪：
用戶：幫我規劃一個三天的東京旅行。
模型：[提供旅行計劃]

第二輪（考驗上下文理解）：
用戶：如果預算減半，應該怎麼調整？
模型：[基於之前計劃調整]
```

**評分標準（1-10分）：**
- 1-2分：無用或有害
- 3-4分：部分有用但有明顯錯誤
- 5-6分：基本回答了問題
- 7-8分：高品質回答
- 9-10分：卓越回答

## 5. LiveBench & WildBench

### LiveBench（避免資料污染）

**創新點：**
- 每月更新測試集
- 使用最新資料（模型訓練截止後）
- 減少訓練資料洩漏影響

**測試類別：**
```
推理：數學、編碼、資料分析
知識：問答、多語言
指令遵循：複雜指令、多步驟任務
```

### WildBench（真實世界評估）

**資料來源**：從實際用戶對話中收集。

**優勢：**
- 反映真實使用場景
- 不是學術化的測試題
- 更難被"刷分"

### 按評估目標選擇

| 評估目標 | 推薦基準 | 原因 |
|---------|---------|------|
| **通用能力** | Open LLM Leaderboard | 多任務覆蓋，易於比較 |
| **知識廣度** | MMLU, C-Eval | 多學科測試 |
| **推理能力** | BIG-Bench, GSM8K | 邏輯和數學推理 |
| **對話能力** | MT-Bench, AlpacaEval | 多輪對話，實用性 |
| **真實性** | TruthfulQA | 避免誤導資訊 |
| **避免資料洩漏** | LiveBench | 持續更新 |
| **中文評估** | C-Eval, CMMLU | 中文專用 |

### 按應用場景選擇

```
教育應用 → MMLU（知識）+ GSM8K（推理）
客服聊天機器人 → MT-Bench（對話）+ TruthfulQA（準確性）
程式碼助手 → HumanEval + MBPP（程式碼生成）
通用助手 → AlpacaEval + Open LLM Leaderboard
```

## ⚠️ 基準測試的局限性

### 1. 資料洩漏（Data Contamination）

**問題**：模型可能在訓練時見過測試資料。

**例子：**
```
某開源模型在 MMLU 上得分 85%，看起來很好...
但深入分析發現：訓練資料中包含了 MMLU 的問題！
→ 實際泛化能力可能遠低於 85%
```

**檢測方法：**
- N-gram 重疊分析
- 使用全新的測試集（如 LiveBench）

### 2. 基準過擬合（Benchmark Overfitting）

模型開發者可能過度優化特定基準，損害通用能力。

### 3. 無法評估的能力

基準測試通常缺少：
- 創造力
- 長文字理解（>10K tokens）
- 多模態能力
- 實時學習能力
- 工具使用能力

### 4. 評估成本

運行完整的 BIG-Bench 可能需要數千美元的 API 呼叫費用。

## 🛠️ 實際評估流程

### 使用 LM Evaluation Harness

```bash
# 安裝
pip install lm-eval

# 運行 MMLU 評估
lm_eval --model hf \
    --model_args pretrained=meta-llama/Llama-2-7b-hf \
    --tasks mmlu \
    --device cuda:0 \
    --batch_size 8

# 運行多個基準
lm_eval --model hf \
    --model_args pretrained=your_model \
    --tasks mmlu,hellaswag,arc_challenge,truthfulqa_mc \
    --output_path results/
```

### 解讀評估結果

```json
{
  "results": {
    "mmlu": {
      "acc": 0.658,
      "acc_stderr": 0.0038
    },
    "hellaswag": {
      "acc": 0.847,
      "acc_norm": 0.862
    }
  }
}
```

**關鍵點：**
- `acc`：準確率
- `acc_stderr`：標準誤差（評估結果的可信度）
- `acc_norm`：歸一化準確率（考慮選項數量）

## 🎯 最佳實踐建議

1. **不要只看總分**：深入分析各子任務表現
2. **組合多個基準**：彌補單一基準的盲點
3. **關注標準誤差**：小幅領先可能是統計噪音
4. **檢查資料洩漏**：對異常高分保持警惕
5. **補充人類評估**：基準分數不能完全代表實用性
6. **持續監控**：模型在實際應用中的表現可能不同

## 🎯 總結

通用評估基準提供了標準化的模型比較方式，但應該：

✅ 使用多個基準全面評估
✅ 關注具體任務表現而非總分
✅ 結合實際應用場景選擇基準
✅ 警惕資料洩漏和過擬合

❌ 不要只依賴基準排名做決策
❌ 不要忽視基準測試的局限性
